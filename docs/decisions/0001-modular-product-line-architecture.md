# ADR-0001：采用模块化制造产品线架构

- 状态：`ACCEPTED_FOR_IMPLEMENTATION`
- 日期：2026-08-10
- 决策范围：FT MES、QMS、WMS、BPI、Lab、Reliability、EHS、Energy 及共享 ADP 平台能力

## 背景

当前恢复仓库包含 250 个 Maven 模块、80 个 Compose 服务、398 个历史可导航页面和多个年代的业务包。
这些资产证明了系统的覆盖范围，但没有形成可独立发布、独立成熟和按需部署的产品边界。继续按一个大系统修复，
会让任何模块的缺陷都阻塞整体发布，也会让小客户承担无关服务、数据库迁移和运维成本。

## 决策

采用“共享底座 + 领域产品 + 组合方案”的软件产品线架构：

1. `FT Platform Foundation` 和 `FT Manufacturing Foundation` 是所有领域产品的共享硬依赖。
2. MES、QMS、生产仓储、追溯、BPI、Lab、Reliability、EHS、Energy 是独立成熟度和发布单元。
3. 跨产品集成使用版本化 API/事件契约、inbox/outbox 和幂等键，不允许新增跨产品数据库写入。
4. 商业版本和行业方案由 manifest 组合，不形成永久行业/客户代码分支。
5. 部署单元可以按客户规模合并，但 Java 包、schema、Flyway location、权限和验收责任保持隔离。
6. PostgreSQL 是默认数据库；Oracle 只保留为隔离的 legacy template。

权威产品关系见
[FT 制造软件模块化产品矩阵](../product/ft-mes-modular-product-portfolio.md)。

## 被考虑的替代方案

### 单体大套件

优点是现状改动少；缺点是发布耦合、运维重、成熟度不可解释。拒绝。

### 基础/专业/旗舰逐级继承

优点是销售简单；缺点是高版本成为所有模块的并集，不能解决内部耦合。拒绝。

### 行业永久分支

优点是短期定制快；缺点是公共修复和数据库迁移持续漂移。拒绝。

### 每个能力立即微服务化

优点是物理隔离；缺点是当前会放大部署、网络、事务和可观测性成本。拒绝立即全面实施，保留按证据拆分。

## 结果

### 正向结果

- 小客户可以只部署 MES Start；QMS、WMS、BPI、EHS 等按需增加。
- 每个产品都有独立成熟度、版本、验收和回滚门禁。
- 行业差异优先落在清单、模板和适配器中，公共修复仍回到 `main`。
- Java 21、文件服务和数据库替换可以按部署单元分阶段升级，不要求 60GB 业务代码一次切换。

### 成本和约束

- 必须补齐产品 manifest、契约版本、schema 所有权和独立 E2E。
- 历史跨表查询和共享数据库写入需要渐进拆除。
- 在边界稳定前，部署仍可物理合并，不能把“尚未拆服务”误判为“产品不能拆”。
- 产品矩阵和实际菜单、Compose profile、Flyway migration 必须由 CI 校验一致。

## 非功能要求

- 产品未启用时，其菜单、消费者、调度器和迁移不得启动。
- 集成下游不可用时，本域事实可保存，跨域动作进入可重试 outbox 或失败关闭状态。
- 所有跨域命令必须可幂等重放并可追溯到来源业务版本。
- 文件、审计、身份和消息等共享能力必须有容量、备份恢复和降级策略。
- M4 产品必须提供容量、安全、灾备、升级回滚和现场业务签字证据。

## 后续动作

1. 给当前能力、服务、路由、权限、数据库迁移和测试标注 `productId`。
2. 先生成 `MES Start` 清单，再形成 `MES Standard` 和 `Process Intelligence`。
3. 禁止新增跨产品表依赖，并登记现有依赖的替换计划。
4. 每个领域产品建立独立 release gate 和回滚演练。
