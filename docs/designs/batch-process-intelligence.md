# CEO Plan: 智能批次与工艺数据中心（BPI）

Generated by `/plan-ceo-review` on 2026-07-12

## 0. 执行摘要

本计划建设一个放在 MES 产品中的独立模块：**智能批次与工艺数据中心**
（Batch & Process Intelligence，BPI）。它不替代 PLC/DCS 控制，不替代 JetLinks
数采，不替代 WOM、QCS、WMS，而是把测点、设备状态、生产指令、物料、质量和
能耗转化成可审计的生产事实。

核心判断：模型训练质量首先受制于批次边界、时间对齐、测点语义、质量标签和
人工修订血缘，而不是算法。因此首期同时交付生产事实底座、智能批次产品和训练
数据治理，但不允许模型直接闭环控制设备。

成功标准不是“接口 200”或“页面可见”，而是每个批次可以从真实页面追溯到事件、
规则版本、PostgreSQL 业务事实、IoT 原始时间范围、质量结果、WMS 库存动作和训练
数据集版本。

## 1. 第一性原理：四轮推演

### 第一轮：真正的问题

表面问题是自动生成批次，真实问题是连续生产过程中不存在天然、可靠、统一的批次
边界。流量、阀门、泵、罐液位、指令和质量结果分别只能提供部分证据。产品必须管理
“证据如何形成事实”，而不是用一个定时任务猜批次。

### 第二轮：不可妥协的事实属性

一个可训练、可审计的批次必须同时具备：

1. 稳定身份：批次 ID 一经发布不因规则升级改变。
2. 双时间：设备事件时间和平台接收时间同时保留。
3. 可复现：保留规则、工艺路线、配方、测点语义和标定版本。
4. 可修订：人工修订追加版本，不能覆盖原始判断。
5. 可解释：每个边界有证据集合、置信度和缺失项。
6. 可核对：物料、干物、能源和质量存在平衡与差异账。
7. 可关联：能关联 WOM 指令、QCS 检验、WMS 单据和上下游批次。

### 第三轮：规模约束

十万测点、每分钟 15 个点等于平均约 25,000 点/秒、21.6 亿点/天。若每点连同索引、
时间和消息开销按 50-200 字节估算，日数据量约 108-432 GB。单体 MES、单 PostgreSQL
业务库和当前单 broker 测试 Kafka 都不能直接承载。

因此必须在边缘采样、事件传输、流计算、业务事实和离线训练之间分层，MES 只接收
批次相关事实与聚合，不接收全部原始点。

### 第四轮：模型训练约束

训练样本不是“按 batch_id join 几张表”。必须执行时间点正确关联，防止未来质量结果
泄漏到过去特征；训练集必须冻结数据范围、特征定义、标签定义、修订版本和源码版本。
低置信度或未人工确认的自动批次不得默认成为监督学习金标准。

## 4. What Already Exists

### MES 仓库

- `material-wms`：已实现完工入库、质检释放、生产领料、幂等和 PostgreSQL marker 验收。
- `process-analysis`：已实现 WOM/QCS/WMS 只读追溯和 `pa_trace_snapshots`。
- WOM：拥有制造指令、投料、执行、报工和请检入口。
- QCS/LIMS：拥有检验、结果和处置事实，数据完整性仍需按真实环境逐项验收。
- PostgreSQL-first、Nacos、网关、Docker 和真实页面/API/落库验收框架已经存在。

### IoT 仓库

- JetLinks Community 2.10，Java 17、Spring Boot 3.4.7、WebFlux、R2DBC。
- MQTT Client/Server、设备网关、协议解码、物模型、规则引擎和内部 EventBus。
- 设备属性主题 `/device/{productId}/{deviceId}/message/property/report`。
- `TimeSeriesMessageWriterConnector` 已把设备消息写入 TimescaleDB/ThingsDataWriter。
- 支持 TimescaleDB、TDengine 和 Elasticsearch 适配。

### 明确不重复建设

- 不在 MES 再建 PLC/Modbus/MQTT 协议驱动。
- 不在 BPI 保存全部原始测点。
- 不让 ProcessAnalysis 反向拥有生产事实。
- 不复制 WOM、QCS、WMS 的交易和状态字段。
- 不用生成模块元数据代替清晰的源码服务边界。

## 5. 产品模块与用户

### 用户角色

| 角色 | 主要任务 | 关键权限 |
|---|---|---|
| 调度/班长 | 监控当前批次、处理候选和异常结束 | 确认、暂停、强制结束，不可改规则 |
| 工艺工程师 | 配置工段、拓扑、规则、公式和阈值 | 草拟、模拟、提交规则版本 |
| 质量人员 | 关联样品、确认质量处置和标签 | 质量关联、释放/拒绝，不可改原始事件 |
| 物料/仓储 | 核对完工、批号、数量和库存状态 | 触发/复核 WMS 动作 |
| 数据工程师 | 管理测点语义、数据质量、数据集 | 数据集快照，不可修改生产事实 |
| 审批人 | 发布规则和重大人工修订 | 双人审批、电子审计记录 |
| 系统管理员 | 租户、权限、集成和运维 | 不自动拥有工艺审批权限 |

### 页面信息架构

1. **实时生产态势**：按产线显示指令、当前批次、阶段、置信度、累计量和数据健康度。
2. **批次审核队列**：只突出需要人处理的候选、冲突、断流、切罐和超差。
3. **批次详情**：时间轴、边界证据、参数曲线、物料/能源平衡、质量、谱系和审计。
4. **规则与模拟**：二维工艺拓扑、测点绑定、开始/结束/切换规则、历史回放对比。
5. **数据质量中心**：时钟漂移、坏质量、断点、重复、乱序、单位和标定问题。
6. **调账与修订**：自动值、人工值、差异、原因、附件和审批。
7. **训练数据管理**：特征版本、标签版本、批次范围、排除原因、快照和实验链接。

| 层 | 首选技术 | 决策说明 |
|---|---|---|
| IoT 核心 | 现有 JetLinks 2.10 / Java 17 | 不 fork 核心协议逻辑，新增独立 exporter 模块 |
| IoT 热时序 | TimescaleDB pilot | 先复用现有能力；全厂前与 TDengine 做真实压测门禁 |
| 事件总线 | Kafka 4.2.x KRaft，3 broker 起 | 采用稳定补丁线；生产不使用当前 ZooKeeper 单 broker 编排 |
| Schema | Protobuf + Apicurio Registry | Java/Flink/Python 多语言；禁止无版本 JSON map 成为公共契约 |
| 流计算 | Flink 2.2.x / Java 17 | 与当前稳定 K8s Operator 兼容，采用 event time/checkpoint/savepoint |
| 流状态 | Embedded RocksDB + S3/MinIO checkpoint | 软件累积量、规则广播状态和事件时间 timers 可恢复 |
| MES BPI Service | Java 17 / Spring Boot 3.4 独立 Maven 工程 | 新权威领域不进入已 EOL 的 Java 8/Spring Boot 2.1 技术栈 |
| Legacy Adapter | Java 8/Spring Boot 2.1 薄适配模块 | 只负责 Nacos、旧网关、RBAC/tenant 上下文和协议转发，不拥有领域状态 |
| MES 业务库 | 独立 `ft_mes_bpi` PostgreSQL 15+ 数据库 | 只存业务事实、事件索引、聚合、审计和 outbox/inbox；独立 service role |
| 冷数据/离线 | MinIO + Apache Iceberg + Parquet | 存原始选择流、聚合、特征和不可变数据集快照 |
| 查询计算 | Trino 或 Spark SQL（二期） | 训练和批量重算，不进入首期在线链路 |
| MLOps | Python 3.12 + MLflow 3.x | 实验、数据集、指标、模型和源码版本血缘 |
| Feature Store | Feast（三期） | 只有在线推理出现后才启用在线 store；首期保证 point-in-time 兼容 |
| 可观测性 | OpenTelemetry + Prometheus + Grafana + Loki | eventId/batchId/orderId 贯穿日志、指标和 trace |

版本采用“稳定补丁线 + 每半年升级评审”，不把 `latest` 写入生产编排。

### 旧平台兼容边界

浏览器仍访问 MES 统一入口。Java 8 adapter 从既有 Keycloak/RBAC 上下文提取 tenant、user、
roles 和 traceId，以短时签名的内部 JWT 传给 BPI；BPI 必须再次执行对象级权限校验，不能
信任前端 header。adapter 使用固定 upstream 和 mTLS，不接受用户传入任意目标 URL，避免
代理型 SSRF。BPI 暂不依赖旧 Nacos client；adapter 负责旧服务发现，现代服务通过内部 DNS/
反向代理寻址。Phase 0 必须验证 token 过期、角色变更和跨 tenant 拒绝路径。

### 数据库与 migration

BPI 使用独立数据库 `ft_mes_bpi` 和最小权限 service role；旧 adapter 没有该库写权限。
Flyway migration 是唯一 schema 来源，开发、Compose、integration 和 production 均运行同一
版本化 migration。`deploy/docker/postgres/init` 只负责创建数据库/role 和启动 migration
container，不复制第二套 `CREATE TABLE`，防止 init SQL 与服务 migration 漂移。

### 构建与分发

- `contracts/bpi-events` 生成并发布 Java JAR、Python wheel 和 Protobuf descriptor；Apicurio
  compatibility gate 禁止删除/复用 field number 和破坏性类型变更。
- `bpi-service`、`batch-intelligence-adapter`、`mes-event-exporter` 发布带 git SHA 和 SBOM 的
  OCI image；`batch-event-engine` 发布 versioned job JAR + image + savepoint compatibility 元数据。
- CI 使用 Java 8/17 toolchain matrix，执行 proto breaking check、Maven tests、container scan、
  Compose render 和跨版本 contract tests；仅签名镜像可进入 staging。
- 开发镜像可进入 GHCR；生产 registry、签名和制品保留策略在 Phase 0 固化。

### 规则运行与回放同源

实时计算、历史回放和规则模拟必须调用同一个 `batch-rule-runtime` Java 17 library 和同一
rule AST，不允许 BPI/Java 8 adapter 另写一套 evaluator。BPI 只提交 simulation job、保存
输入 manifest 和读取结果；相同事件集合、rule/topology/calibration 版本必须生成相同 checksum。

## 8. IoT 到 MES 事件契约

### `TelemetryEnvelopeV1`

```protobuf
message TelemetryEnvelopeV1 {
  string event_id = 1;
  string message_id = 2;
  string tenant_id = 3;
  string plant_id = 4;
  string line_id = 5;
  string gateway_id = 6;
  string product_id = 7;
  string device_id = 8;
  int64 event_time_ms = 9;
  int64 ingest_time_ms = 10;
  uint64 sequence = 11;
  repeated PointValue points = 12;
  map<string,string> headers = 13;
  uint64 source_epoch = 14;
  SequenceOrigin sequence_origin = 15;
}

message PointValue {
  string property_id = 1;
  oneof value { double double_value = 2; int64 long_value = 3;
                string string_value = 4; bool bool_value = 5; }
  string unit = 6;
  string quality_code = 7;
  int64 sample_time_ms = 8;
  string calibration_version = 9;
}

enum SequenceOrigin {
  SEQUENCE_ORIGIN_UNSPECIFIED = 0;
  DEVICE = 1;
  GATEWAY = 2;
  EXPORTER = 3;
}
```

约束：

- `event_id` 全局唯一；重放保持不变。
- `sequence` 按 gateway/device/source_epoch 单调递增；重启必须增加 typed `source_epoch`。
- 去重键为 `(gateway_id, device_id, source_epoch, sequence)`，`event_id` 用于跨系统追踪。
- `event_time` 是 Unix UTC epoch milliseconds，来自设备或网关校时；`ingest_time`
  同样为 UTC，由 JetLinks 生成；本地时区只用于界面展示。
- `quality_code` 至少支持 GOOD、UNCERTAIN、BAD、STALE、SUBSTITUTED。
- 单位必须来自受控字典；单位变化属于测点语义新版本。
- 单消息批量携带同设备同采样周期的多个点，降低 MQTT/Kafka 开销。

设备没有原生 sequence 时，由持久化网关或 exporter 生成并标记 `sequence_origin`。Exporter
epoch 和 counter 必须落本地 RocksDB/数据库并在重启时增加 epoch；这只能保证平台下游有序，
不能证明设备侧未重发，因此结合 MQTT messageId/源 payload fingerprint 做短窗去重并降低
置信度。P1 批次边界信号在生产启用前必须具备设备或网关级可靠 sequence。

Exporter spool 使用有界磁盘队列并按 eventId 保留顺序，容量目标覆盖至少 30 分钟 P1/P2
峰值流量。达到 70%/85%/95% 分别告警、提高非关键点采样间隔、停止 P3/P4 输出；P1 required
事件不得静默丢弃。磁盘满或损坏时停止对应 gateway 的自动批次资格并生成 CRITICAL incident，
JetLinks 原时序写入保持运行。恢复后按原 eventId/sequence 重放，不能生成新身份。

### Kafka 主题

| Topic | Key | Retention | Producer | Consumer |
|---|---|---:|---|---|
| `iot.telemetry.selected.v1` | plant+device | 3-7d | exporter | Flink、cold sink |
| `iot.equipment.state.v1` | plant+asset | 14d | Flink | batch engine |
| `mes.production.context.v1` | order/task | 30d | MES outbox | Flink |
| `bpi.boundary.rule-publication.v1` | tenant+line+rule+version | 180d compacted | BPI outbox | Flink broadcast state |
| `bpi.batch.candidate.v1` | line+rule | 30d | Flink | BPI inbox |
| `bpi.batch.fact.v1` | batchId | 180d | BPI outbox | trace/WMS/data lake |
| `bpi.data-quality.v1` | source+point | 30d | exporter/Flink | BPI data quality |
| `bpi.training.snapshot.v1` | datasetId | 365d | dataset service | ML pipeline |
| `*.dlq.v1` | source key | 30d | each consumer | ops replay tool |

生产分区数由压测决定；初始建议 selected telemetry 96 partitions，其余 12-24。原始选择
流按 device 保持设备内有序；Flink 标准化后必须显式 repartition 到
`plant+line+rule_locality_group` 再执行多信号规则。规则发布时校验它引用的信号属于同一
locality group；超大产线按 asset group 切分，跨组规则通过低频 context stream 汇合。
禁止按 pointId 造成热点，也禁止把整条超大产线强行压到一个 key。

候选事件使用确定性 `candidate_key`，不能依赖 Flink 重启后重新生成的 eventId。START key
采用 UUIDv5(namespace, tenant|line|ruleVersion|contextOrderId|firstQuorumEvidenceEventId)；
END key 采用 UUIDv5(namespace, batchId|ruleVersion|firstEndQuorumEvidenceEventId)。贡献事件 ID
来自源事件且重放保持稳定，因此不会因 checkpoint 重放制造第二个候选；eventId 只负责 trace。
`bpi_inbox_events` 对 source+candidate_key 建唯一约束。

## 9. 采样、流量积分与质量

### 采样分级

| 等级 | 典型信号 | 策略 |
|---|---|---|
| P0 | 联锁、安全控制 | 保留 PLC/DCS；BPI 只读事件，不参与控制 |
| P1 | 阀、泵、罐切换、指令 | 状态变化立即发布，周期心跳 30s |
| P2 | 瞬时流量、波美、温度、压力 | 稳态 4s；切换窗口 0.5-1s；死区+最大静默时间 |
| P3 | 电、汽、水、气 | 10-60s 窗口聚合，并保留峰值/最小值/积分 |
| P4 | 诊断点 | IoT 本地保存，按需查询，不默认进入 Kafka |

### 软件累积量

```text
q_canonical = convert(q_raw, source_unit, canonical_unit)
deltaVolume = (q_prev_canonical + q_curr_canonical) / 2 * deltaSeconds
```

标准体积流量统一换算为 `m3/s` 后积分得到 `m3`；质量流量统一换算为 `kg/s` 后积分得到
`kg`。若现场源单位为 `m3/h`，换算阶段除以 3600，而不是把 `/3600` 隐藏在积分公式中。
单位字典、换算因子、物料和标定版本均受控；缺单位、未知单位或运行中单位变更时冻结
累计器并产生 incident，禁止盲算。

仅在两点质量可接受、间隔小于 `maxGap`、单位已归一且设备状态允许时积分。发生断点时：

- 间隔小于插值阈值：线性插值并降低置信度；
- 间隔超过阈值：生成 gap，不静默补零；
- 迟到事件在 watermark 允许范围内重算窗口；超限进入修订队列；
- checkpoint 恢复后依据 source epoch、sequence、event_id 和累计器版本去重。

重放同一事件集合必须得到数值等价结果；采用 decimal/fixed-scale 或严格定义的 double
求和算法与舍入策略，不允许因并行度变化产生不可解释漂移。

湿质量和干物质量：

```text
wetMass = integral(flow * density(material, baume, temperature))
dryMass = integral(flow * density(...) * solidsFraction(material, baume, temperature))
```

密度和固形物函数必须是物料专属、版本化的标定曲线；波美值不能被当成通用线性换算。

共享总管流量必须先保留物理 meter 原始累计，再按版本化 allocation rule 分配给并发消费者。
支持固定比例、阀路独占、优先级和基于下游支路计量的比例校正；首期不允许凭“当前活动批次
数量”平均分。共享 meter 未配置规则或分配和不守恒时标记 `SHARED_UNALLOCATED`，相关批次
不能自动关闭，避免同一总管量被多个批次重复计算。

Phase 1 仅启用阀路独占、固定比例和人工确认三种无循环模式。基于下游计量的比例校正必须在
Phase 2 证明依赖图无环，并以原始物理总量为守恒上限；若分配结果反过来成为自身输入，规则
发布校验直接拒绝。

## 10. 工艺拓扑与规则 DSL

### 拓扑对象

- 节点：工段、罐、仓、反应器、蒸发器、色谱柱、结晶器、离心机、干燥机。
- 边：管线、输送、分流、合流、回配、外排。
- 执行器：泵、阀、称量、切换阀组。
- 测点绑定：流量、液位、压力、温度、波美、Brix、能耗、设备状态。
- Locality group：产线内需要在同一 Flink key 上联合判断的一组节点和测点，目标不超过
  5,000 events/s/group；拓扑工作台必须可视化分组和预计速率。
- 每次发布生成 immutable `topology_version`，运行批次固定引用该版本。

规则 context 必须声明 `locality_group_code`。跨组规则显式标记 `cross_group=true`，只能通过
低频 context stream 汇合，并在发布前提示更高延迟 SLA；不能暗中跨 partition 做无界 join。

### 规则结构

```json
{
  "ruleCode": "S05_CHROMATOGRAPHY_FEED",
  "version": 3,
  "context": {"requiresOrder": true, "lineId": "L01"},
  "start": {
    "required": ["order.active"],
    "quorum": 2,
    "evidence": [
      {"signal": "feed.flow", "op": ">", "value": 2.0, "for": "10s", "weight": 0.35},
      {"signal": "feed.pump", "op": "==", "value": true, "for": "3s", "weight": 0.20},
      {"path": "TANK_A->COLUMN_1", "op": "OPEN", "weight": 0.25},
      {"signal": "column.level", "op": "RISING", "for": "15s", "weight": 0.20}
    ]
  },
  "end": {"flowBelow": 0.5, "for": "20s", "or": ["path.changed", "target.changed"]},
  "lateness": "30s", "maxGap": "20s", "minimumDuration": "2m"
}
```

禁止首期引入任意 JavaScript/Groovy 表达式。规则 UI 生成受 JSON Schema 约束的 AST，
Flink 使用 Broadcast State 动态加载已发布规则，BPI 保留完整规则版本和审批。

首期规则运行器使用 `KeyedBroadcastProcessFunction`、event-time timer 和显式窗口状态，
不把动态 DSL 编译成 Flink CEP `Pattern`。规则发布通过 broadcast state 更新，无需重启 job；
Flink CEP 只允许未来用于版本固定、随作业发布的静态设备序列，不属于首期批次 DSL。

`for` 明确定义为事件时间连续满足时长，不是处理时间或样本数。每个 evidence 同时要求
`maxSilence`：超过该时长没有新样本时条件转为 UNKNOWN，而不是沿用最后值。Flink 对空闲
source/partition 配置 idleness，避免单个离线设备阻塞全局 watermark。规则的 allowed
lateness、watermark delay、maxSilence 和 timeout 必须作为版本内容参与回放。

`quorum` 是进入置信度计算前必须分别判定为 TRUE 的最小证据数量；未达到 quorum 时不计算
候选分数。required 硬约束失败时直接禁止候选，不能由其他高权重证据抵消。

### 置信度

```text
base = sum(weight * evidenceScore * dataQualityFactor) / sum(allConfiguredWeights)
confidence = clamp(base * (1 - penaltyFactor), 0, 1)
```

所有数值范围均为 `[0,1]`。`evidenceScore` 是阈值匹配程度；quality factor 默认
GOOD=1.0、UNCERTAIN=0.5、SUBSTITUTED=0.3、BAD/STALE=0；`penaltyFactor` 是多个惩罚
按配置上限合成后的比例。分母使用全部已配置权重，缺失证据不能通过缩小分母抬高分数。

| Penalty | Trigger | Default cap |
|---|---|---:|
| interpolation | 窗口内插值样本比例 | 0.30 |
| gap | 窗口内 gap 时长比例 | 0.40 |
| late | watermark 后到达事件比例 | 0.20 |
| unit uncertainty | 使用未校准 fallback 换算；生产默认禁止 | 0.10 |
| degraded equipment | 泵/阀状态 UNCERTAIN/STALE | 0.20 |
| missing signal | 已配置证据没有样本 | 0.50/项 |

`penaltyFactor=min(sum(individualPenalty), maxCompositePenalty)`，默认总上限 0.80。每项 cap、
合成方式和总上限都属于 rule version，pilot 必须校准；硬约束错误仍直接阻断，不降级成惩罚。

- `<0.60`：只记录检测，不创建候选；
- `0.60-0.85`：创建候选，必须人工确认；
- `>=0.85`：允许自动进入 ACTIVE，但仍保留可撤销审核窗口；
- 生产指令缺失、唯一目标罐冲突、关键测点 BAD 时禁止自动确认，不以高分覆盖硬约束。

阈值必须按工段通过历史回放校准，不能全厂共用。

## 11. 批次状态机

```text
DETECTING
   │ 证据达到候选阈值
   v
CANDIDATE ──拒绝/过期──> VOIDED
   │ 自动高置信或人工确认
   v
ACTIVE ──数据/上下文冲突──> SUSPENDED ──恢复/人工处理──> ACTIVE
   │ 结束条件满足
   v
END_CANDIDATE ──恢复流量/误判──> ACTIVE
   │ 稳定窗口完成
   v
CLOSED_RAW
   ├─正常关闭/核对──────────────> RECONCILING
   └─重大迟到证据──────────────> AMENDING
                                     │ 修订审批完成，写新版本并重算
                                     v
RECONCILING ──重大迟到证据──────> AMENDING
   ├─超差──> REVIEW_REQUIRED ──审批修订──> RECONCILING
   │
   └─平衡通过
   v
WAIT_QA ──不合格──> REJECTED ──处置──> DISPOSED/REWORK
   │ 合格释放
   v
RELEASED ──幂等完工入库──> INBOUNDED
```

非法转换通过数据库乐观锁 `revision`、状态转换表和领域服务三层阻止。任何强制结束、
拆批、并批、改量、改时间都生成 correction 事件和审批记录，不执行原地覆盖。

迟到证据在 ACTIVE/END_CANDIDATE 内按 watermark 正常重算；在 CLOSED_RAW、RECONCILING
阶段若影响超过规则版本中的 significance threshold（默认候选值为批次累计量 1% 或边界
30 秒，必须按工段校准），进入 AMENDING。WAIT_QA 以后不自动倒退：创建高优先级修订，
冻结 RELEASED/INBOUNDED 联动，由授权人员决定更正单、库存调账和质量重判。所有下游
更正以补偿事件执行，不删除已发布事实。

AMENDING 内由授权人员审批 correction；BPI 按修订后的边界、累计量和谱系写入新 revision，
随后明确返回 RECONCILING 重新执行守恒和超差核对。核对通过才允许进入 WAIT_QA；核对失败
继续 REVIEW_REQUIRED，不能从 AMENDING 直接跳到 RELEASED 或 INBOUNDED。

普通 DELETE，数据修订通过新版本实现。

插值方法和对象存储 definition checksum；超出适用范围返回 OUT_OF_RANGE，不做外推。
批次通过 topology version 间接固定单位字典和标定曲线版本，保证历史重放使用原版本。

设备拓扑允许物理回路；批次实例谱系保持时间 DAG。母液 S11 批次回配到未来 S07 新批次
是合法边，不是图环。插边时要求 parent 和 child 不是同一实例、物料移动时间不早于 parent
产出且不晚于 child 消耗允许窗口，并执行 `child -> parent` 可达性检查；发现真正祖先环时拒绝。

Flink 高频检查点保存在 state backend 和冷事件流，PostgreSQL 的
`bpi_virtual_totalizers` 只 upsert 最新摘要，小时表用于长期查询，避免形成每日百万级检查点表。

### 查询

- `GET /bpi/v1/batches?lineId=&state=&from=&to=`

- `GET /bpi/v1/batches/{id}/evidence`
- `GET /bpi/v1/batches/{id}/genealogy`
- `GET /bpi/v1/batches/{id}/balance`
- `GET /bpi/v1/data-quality/incidents`

### 命令

- `POST /bpi/v1/candidates/{id}/confirm`
- `POST /bpi/v1/candidates/{id}/reject`
- `POST /bpi/v1/batches/{id}/suspend`
- `POST /bpi/v1/batches/{id}/force-close`
- `POST /bpi/v1/batches/{id}/corrections`
- `POST /bpi/v1/rules/{id}/simulate`
- `POST /bpi/v1/rules/{id}/publish`
- `POST /bpi/v1/datasets/{id}/snapshots`

命令必须要求 `Idempotency-Key`、`If-Match revision` 和明确 reason；高风险命令走审批。
WOM、QCS、WMS 通过 adapter 接口集成，不让领域服务直接访问对方内部表。过渡期允许
只读 repository 查询旧表，但必须集中在 `legacy-adapter` 包并列入退场计划。

任何会触发外部副作用的状态转换，业务状态、`bpi_outbox_events` 和审计记录必须在同一
PostgreSQL 事务提交。Outbox publisher 采用 at-least-once 投递，接收端按 idempotency key
去重；首期用 `FOR UPDATE SKIP LOCKED` 轮询，后续可替换 Debezium 而不改变事件契约。
巡检任务持续检测 RELEASED 超过 5 分钟但既无 INBOUNDED、无 pending outbox、也无明确
失败记录的批次，并阻断静默库存差异。

QA gate 的首选触发是 QCS/LIMS 在检验申请中保存 BPI batchId，并通过 adapter event/outbox
回传最终 disposition；遗留模块暂不支持事件时，BPI 每 30 秒幂等轮询作为兼容路径。仅靠
sample_time 落在批次区间只能产生待确认关联，不能自动释放。配方/工艺版本定义 required
inspection set，全部必检项 final=ACCEPT 后触发 WAIT_QA -> RELEASED；QCS 不可用时保持
WAIT_QA 并生成 `quality_gate_blocked`。

BPI 是 WMS 完工入库命令发起方：RELEASED 事务内写入 deterministic
`WmsInboundCommand` outbox；WMS 以 idempotency key 处理并回传 documentId/status，BPI
收到成功回执后进入 INBOUNDED。超时必须先按 key 查单再重试，禁止盲目重复创建单据。

## 15. 四条数据路径及影子路径

### Happy Path

```text
设备值 -> JetLinks 解码/物模型 -> exporter 校验/标准化 -> Kafka
     -> Flink 去重/事件时间/积分/规则 -> batch candidate
     -> BPI inbox/状态机/PostgreSQL -> 用户确认或自动确认
     -> QCS 质量 -> RELEASED -> WMS 完工入库 -> trace/dataset
```

### Nil Path

```text
缺 envelope deviceId/eventTime -> 整个 envelope 进入 quarantine，不进入业务流
单个 PointValue 缺 propertyId/unit/value -> 只剥离该点到 point-reject stream
                                      -> 其余有效点组成 reduced envelope 继续
                                      -> rejected point 保留 parent eventId 和 incident
```

指标分别统计 `iot_export_events_rejected_total` 与 `iot_export_points_rejected_total`；禁止一个
坏点导致同 envelope 的流量、温度等有效点一起丢失。若被剥离的是规则 required 关键点，
对应规则转 UNKNOWN 并在实时态势显示受影响范围。

### Empty Path

```text
消息存在但 points=[] 或值为空 -> 不按 0 处理
                              -> EMPTY_PAYLOAD 计数/告警
                              -> 不更新累计器和批次证据
```

### Error Path

```text
Kafka/Flink/BPI/WMS 失败 -> 本地缓冲或 Kafka 重放 -> inbox 幂等
                        -> 指数退避/DLQ -> 运维重放
                        -> 页面明确显示延迟/部分数据，不显示假成功
```

端到端语义不是笼统宣称“exactly once”：Kafka/Flink 管理状态采用 checkpoint；Flink 到 BPI
候选为 at-least-once + inbox 去重；BPI 内部为数据库事务；BPI 到 QCS/WMS 为 transactional
outbox + 接收端幂等，因此整体达到可验证的 effectively-once 业务结果。每一跳都有重放和
对账证明。

## 16. Error & Rescue Registry

| Method/Codepath | Failure | Exception/Class | Rescue | User sees |
|---|---|---|---|---|
| Exporter decode | 缺字段/类型错误 | ContractValidationError | quarantine，不重试 | 数据契约异常 |
| Exporter publish | broker 超时 | KafkaPublishTimeout | 本地有界缓冲+退避 | 数据链路延迟 |
| Flink deserialize | schema 不兼容 | SchemaCompatibilityError | DLQ+暂停对应 schema | 指定测点流暂停 |
| Event-time assign | 时钟漂移超限 | ClockSkewError | 标记 BAD/incident | 时钟异常，不参与自动批次 |
| Totalizer update | 负时间/单位变化 | TotalizerInputError | 冻结累计器 | 累积量待复核 |
| Rule evaluation | 缺关键绑定 | RuleContextIncomplete | 禁止自动确认 | 规则上下文不完整 |
| Candidate consume | 重复 event | DuplicateEvent | inbox 幂等忽略 | 无感知 |
| State transition | revision 冲突 | OptimisticLockConflict | 返回 409+刷新 | 数据已被他人更新 |
| Force close | 权限或审批不足 | AuthorizationDenied | 拒绝并审计 | 无权执行该操作 |
| WOM context | 服务不可用 | UpstreamUnavailable | 缓存旧上下文，禁止自动切批 | 指令上下文暂不可用 |
| QCS link | 样品时间不匹配 | QualityLinkConflict | 人工选择并记录原因 | 质量关联冲突 |
| WMS inbound | 超时/重复 | WmsCommandError | 同 key 重试，查单确认 | 入库处理中/失败 |
| Object store write | 不可用 | ArtifactStoreUnavailable | 暂停快照，保留任务 | 数据集生成失败 |
| Dataset build | point-in-time 违规 | LeakageValidationError | 阻断发布 | 训练集存在未来泄漏 |
| MLflow register | 服务不可用 | ModelRegistryUnavailable | 不影响生产批次，任务重试 | 实验登记延迟 |

禁止 catch-all 后吞异常。每次救援日志必须包含 tenant、plant、line、eventId、batchId、
ruleVersion、traceId 和 retryCount；敏感 payload 不写日志。

WOM 缓存上下文带 `cached_context_expiry_seconds`；过期后 ACTIVE 转 SUSPENDED，原因
`UPSTREAM_CONTEXT_STALE`。WOM 恢复或订单取消时通过 reconciliation API/outbox 主动失效
缓存，禁止无限沿用旧指令。

## 17. Security & Threat Model

| Threat | Likelihood | Impact | Mitigation |
|---|---|---|---|
| 伪造设备事件导致错误切批 | Med | High | mTLS、gateway identity、ACL、event signature/来源校验 |
| 重放消息重复累计 | High | High | sourceEpoch+sequence、deterministic candidate key、BPI inbox unique |
| 越权强制结束/改量 | Med | High | RBAC、对象级 tenant/plant 校验、双人审批、审计 |
| 规则被恶意修改 | Low/Med | High | 草稿/审核/发布分权、checksum、不可变版本、回放门禁 |
| SQL/表达式注入 | Med | High | 参数化 SQL；DSL AST 白名单；禁止任意脚本 |
| 跨租户批次泄漏 | Med | High | repository 强制 tenant scope，集成测试和 RLS 评估 |
| 训练集包含敏感人员信息 | Low | Med | 默认不采集 PII，人员标识脱敏，数据集权限独立 |
| 对象存储清单被替换 | Low | High | checksum、versioning、WORM/保留策略、最小权限 |
| sample compose 密码/CORS 进入生产 | Med | High | secrets manager、明确域名、TLS、生产配置扫描门禁 |

OT 到 IT 默认单向上送。首期 BPI 不提供设备写命令；后续建议也必须由人确认并经 MES/PLC
既有安全通道执行。

## 18. Interaction Edge Cases

| Interaction | Edge Case | Handling |
|---|---|---|
| 确认候选 | 双击/多人同时确认 | Idempotency-Key + revision，第二人收到已处理状态 |
| 强制结束 | 页面离开或网络超时 | 服务端任务 ID，可恢复查询，禁止重复结束 |
| 规则发布 | 历史回放仍在运行 | 发布锁定 simulationId，结果 checksum 必须匹配 |
| 批次列表 | 数据持续变化 | cursor 分页+固定查询快照时间，不用 offset 漂移 |
| 曲线加载 | 原始库暂不可用 | 先显示业务事实和明确的“曲线暂不可用”局部状态 |
| 数据质量队列 | 事件数超过 10,000 | 聚合分组、虚拟列表、按影响批次优先级排序 |
| 修订表单 | 旧 revision 提交 | 409，展示差异，不静默覆盖 |
| 数据集生成 | 用户关闭页面 | 后台任务继续，通知中心返回结果 |
| 空生产线 | 无当前批次 | 显示“待生产”及最后心跳，不使用空白大页面 |

所有页面复用统一 `EntityPanel` 状态组件，固定支持 loading/empty/error/partial/success，
避免每页自行拼接不一致状态。Nil/Empty 导致边界检测被抑制时，实时态势必须显示受影响
产线和规则数量，而不只写后台 incident。

## 20. Test Review

### 测试矩阵

| 层 | 必测内容 |

| Unit | 积分、单位换算、共享 meter 分配、置信度、状态机、平衡、DSL validation、point-in-time join |
| Property-based | 乱序/重复后累计量不增加；共享分配与拆分质量守恒；修订 revision 单调 |
| Contract | Protobuf 前后兼容、JetLinks header 映射、Kafka key 和 schema |
| Integration | Kafka+Flink checkpoint/restart、BPI inbox/outbox、PostgreSQL migrations |
| System | WOM 指令 -> 候选 -> QA -> WMS 入库 -> 追溯完整链 |
| E2E | 真实页面、真实 API、唯一 marker、PostgreSQL 查库、清理回滚 |
| Replay | 选定历史时段按规则版本重算，结果 checksum 可复现 |
| Load | 25k/s 基线、50k/s 目标、250k/s 短时峰值，持续 24h 无丢失 |
| Chaos | broker/Flink/BPI/Postgres/MinIO 分别重启，累计量和批次不重复 |
| Security | 越权、跨租户、重放、恶意 DSL、超大 payload、证书轮换 |

“周五凌晨可发布”的测试：在流量持续时依次杀死 exporter、Kafka broker、Flink
TaskManager 和 BPI 实例。对同一冻结事件集合，每次恢复前后累计结果必须数值等价（按固定
scale 舍入后完全一致），不得把事件丢失混入“仪表精度”。另外用现场校准总量核对物理偏差，
阈值由仪表不确定度和工艺标准单独定义。状态事件无重复，QA/WMS 只执行一次，审计链完整。

敌对 QA 测试：同时制造切罐、迟到 45 秒、流量归零、泵状态抖动、指令切换和人工强制
结束，验证只产生一个权威批次且冲突进入审核。

## 21. Performance Review

### 容量门槛

- 设计基线：25k points/s average，50k sustained，250k burst 60s。
- exporter 批次：同设备 100-500ms 或 100-500 points，设置有界内存和磁盘缓冲。
- Flink：按 plant+line+asset 分区；禁止把单条产线全部落到一个超热点 key。
- BPI 写入：只接收候选、状态、窗口和聚合，目标稳态低于原始点流量的 1%。
- PostgreSQL：批次查询 p95 <300ms，命令 p95 <500ms，不含外部 WMS/QCS 延迟。
- 实时态势：端到端正常延迟 p95 <5s；边界候选 p95 <10s。
- 数据集任务与在线库隔离连接池，禁止训练扫描拖垮生产库。

Exporter spool 容量按 `peakEncodedBytesPerSecond * outageWindow * 1.3` 计算，不以固定 GB
拍脑袋；Phase 0 用真实 Protobuf 压缩率测定。Flink keyed state 配置 TTL = 最大批次时长 +
allowed lateness + 修订窗口，超长批次使用显式续期，禁止状态永久增长。Savepoint 升级必须跑
serializer compatibility test。

Iceberg 按 plant/date/hour 组织并运行 compaction，目标文件 128-512 MB；禁止每个设备/批次
生成小文件。Phase 1 实时态势先使用 5 秒条件轮询和 ETag，避免为十几条线立即引入第二套
push 通道；当并发和延迟证明轮询不足时再复用现有 WebSocket/SSE 基础设施。

`bpi_data_quality_incidents` 明细只保留 7 天并按日分区，小时 summary 长期保存。累计器最新
摘要使用 upsert，小时 rollup 按月分区；原始检查点历史留在 Flink state/Kafka/Iceberg。

### 存储分层

- Kafka：3-7 天可重放。
- Timescale/TDengine 热数据：pilot 30 天；全厂按压测确定 7-30 天。
- 1 分钟/批次聚合：至少 2 年。
- Iceberg/Parquet 原始选择流：按合规和成本确定 1-2 年，生命周期转低频存储。
- PostgreSQL BPI 业务事实：在线保存全生命周期，按月分区 append-only 大表。

全厂切换前执行 TimescaleDB 与 TDengine A/B 压测：摄取、压缩率、24h 查询、恢复时间、
运维复杂度均达到门槛后再决定，不在设计阶段凭印象更换现有时序后端。

### Day-1 Dashboard

1. 全链路吞吐与延迟。
2. 每条产线当前批次和数据健康。
3. Kafka/Flink checkpoint/lag/backpressure。
4. 候选批次置信度与人工队列。

## 23. Deployment & Rollout

### 环境

- local：单机 Compose，合成数据，不冒充性能环境。
- integration：Kafka 3 broker、Flink HA、PostgreSQL、MinIO、只读 Trino、JetLinks、MES 全链。
- staging：一条真实产线镜像流，影子批次，不写 WOM/QCS/WMS。
- production：先一条线，逐工段启用，再扩全厂。

### 顺序

```text
1. 发布 schema/兼容性门禁
2. 部署 Kafka/Registry/MinIO/Flink 基础设施
3. 部署 exporter，shadow 输出，不影响 JetLinks 原写入
4. 部署 Flink，生成 shadow candidate
5. 执行 BPI PostgreSQL 向前兼容 migration
6. 部署 BPI API/UI，保持只读
7. 历史回放 + 7-14 天影子对比
8. 开启人工确认，不联动 WMS
9. 开启 QA 关联和幂等 WMS 联动
10. 一条线签字后逐线推广
```

### 回滚

```text
异常发现
  ├─ UI/API 问题 -> 关闭 bpi.ui/bpi.commands feature flag -> 保留采集和 shadow
  ├─ 规则问题 -> 回退 active_rule_version -> 从 savepoint/replay 重算
  ├─ Flink 问题 -> 停止 sink/恢复 savepoint -> Kafka 保留事件
  ├─ Exporter 问题 -> 关闭 exporter -> JetLinks 原时序写入继续
  └─ WMS 联动问题 -> 关闭 integration flag -> outbox 保留，人工核对
```

数据库 migration 采用 expand/contract，不以 DROP 回滚；事件 schema 只做向后兼容新增；
每次生产启用必须有 feature flag、runbook、marker、数据库查询和业务签字。

Feature flag 首期存 `bpi_feature_flags` 并通过 Nacos 推送失效通知，支持 global/tenant/line
scope，服务端本地缓存最大陈旧 10 秒。`bpi.ui` 只影响导航展示，`bpi.commands`、
`bpi.auto-confirm`、`bpi.wms-link` 在服务端强制检查；每次变更写 AuditLog。

## 24. 分阶段实施与验收

### Phase 0：契约与基准（2-3 周人类团队）

- 盘点一条产线 200-500 个关键点、时钟、单位、质量码和设备拓扑。
- 实现 Protobuf schema、兼容性测试和合成事件生成器。
- 建立 Maven toolchains/CI 矩阵：MES Java 8、IoT/Flink Java 17，分别构建后执行跨版本契约测试。
- 验证设备原生 sequence；缺失时实现持久化 gateway/exporter epoch+counter 并标记来源。
- 建立 OCI/JAR/JAR+descriptor/Python wheel 的 build、SBOM、签名、registry 和保留流水线。
- 创建 `ft_mes_bpi` 数据库、Flyway baseline、最小权限 service role 和 migration smoke。
- 完成 Timescale/TDengine/Kafka/Flink 基准压测。
- 验收：持续 24h，无不可解释丢失；测点语义覆盖率 100%。

### Phase 1：影子批次（6-8 周）

- exporter、Kafka、Flink 去重/积分/数据质量、BPI 规则/拓扑/候选/审核页面。
- 部署只读 Trino 查询 Iceberg，支持回放核对和故障诊断，不进入在线事务链路。
- 选择 S01、S02、S05 或现场最容易核对的 2-3 工段。
- 运行 7-14 天影子，不写生产业务状态。
- 验收：边界人工认同率 >=95%，累计量偏差不超过仪表/标定允许范围。

### Phase 2：生产闭环（6-10 周）

- 扩展 S01-S12，加入分流/合流/回配谱系、平衡、QCS 和 WMS 幂等联动。
- 真实页面/API/PostgreSQL marker 验收和回滚演练。
- 验收：主链每步落库、谱系、QA、入库、清理证据齐全；无 HTTP 200 假成功。

### Phase 3：训练数据产品（4-6 周）

- Iceberg 数据层、特征/标签定义、point-in-time 数据集、MLflow。
- 首批模型只做离线：收率预测、质量预测、异常检测或边界评分。
- 验收：相同 manifest 可复现相同训练集；数据泄漏检测通过；低置信样本可排除。

每个 dataset definition 必须定义 `prediction_time`、feature cutoff、label assignment 和
max label delay。特征只能使用 event_time 不晚于 prediction_time 且在当时可获得的数据；
质量结果可以在预测时点后作为监督标签，但必须记录 sample_time、result_available_time 和
labeled_at，且绝不能作为预测时点之前的输入特征。训练/验证按生产时间和批次分组切分，
禁止随机行切分造成相邻批次泄漏。

### Phase 4：建议型智能（后续）

- 在线特征/Feast、模型服务、漂移监控、A/B 或 shadow inference。
- 输出操作建议，不直接控制 PLC/DCS。
- 只有模型性能、漂移、人工采纳和安全评审通过后才扩大使用。

## 25. Design & UX Review

### 用户流

```text
实时态势
  -> 系统检测候选
     -> 高置信自动 ACTIVE / 中置信进入审核队列
        -> 查看证据和曲线
           -> 确认 / 拒绝 / 修订
              -> 批次结束与平衡
                 -> QA 关联与处置
                    -> WMS 入库
                       -> 追溯 / 数据集
```

### 状态覆盖

| Feature | Loading | Empty | Error | Success | Partial |
|---|---|---|---|---|---|
| 实时态势 | skeleton 保持布局 | 待生产+最后心跳 | 链路错误+影响范围 | 当前批次 | 部分点延迟明确标黄 |
| 审核队列 | 行级加载 | 无待处理 | 重试/诊断入口 | 已处理回执 | 曲线不可用仍可审证据 |
| 批次详情 | 分区加载 | 不适用 | 单区错误 | 完整事实 | 质量/WMS 尚未返回 |
| 规则模拟 | 任务进度 | 无历史范围 | 失败原因 | 对比指标 | 部分测点缺失 |
| 数据集 | 后台任务状态 | 无满足条件批次 | 泄漏/质量阻断 | manifest+checksum | 排除样本清单 |

界面应像生产操作台而非营销仪表盘：信息密度高、按异常优先、少卡片、固定表格尺寸、
曲线与证据并排。移动端只支持查看告警和审批摘要；规则设计、谱系和调账以桌面端为主。
所有状态不仅用颜色表达，支持键盘、明确焦点和可读错误信息。

## 26. Long-Term Trajectory

- Reversibility：4/5。Exporter、Flink 和 BPI 均可 feature flag 关闭，原 JetLinks/WOM/QCS/WMS
  继续运行；唯一长期承诺是事件契约和生产事实 ID，必须谨慎治理。
- Phase 2 后，设备巡检、能源分摊、安环事件和高级排产可复用同一生产上下文。
- BPI 领域层在 Java 8 中保持无框架，MES 基座升级后迁移到 Java 17/21 独立服务。
- Schema、规则、拓扑、数据集和模型统一版本链，使未来算法升级不改写历史事实。
- 每半年执行技术版本、容量、存储成本、规则准确率和人工修订率评审。

## 36. Engineering Review Addendum

Engineering review performed on 2026-07-12 against `codex/core-flow-fix` at `ef089b4`.

### Step 0: Scope Challenge

The complete design necessarily spans more than eight files and two services. Product scope remains
accepted because the user selected the full B architecture, but implementation is not a big-bang PR:

- First executable scope is **Phase 0 + Phase 1 shadow batch only**.
- Phase 1 does not write WOM/QCS/WMS production state.
- Phase 2-4 stay in this product design and require separate release gates.
- Contract establishment and benchmark evidence precede all parallel feature work.

This keeps the complete product trajectory while making the first production blast radius reversible.

### Architecture Findings Resolved

|---|---|---|---|
| A1 | P1 / 10 | New authority on Java 8/Spring Boot 2.1 would create immediate EOL debt | Java 17 BPI service + Java 8 thin adapter |
| A2 | P1 / 9 | Contract and container distribution pipeline was absent | JAR/wheel/descriptor/images/SBOM/signing CI added |
